# 轻食记个性减脂计划设计

日期：2026-09-08
状态：已确认，待实施计划

## 1. 目标与范围

在现有账户、七步健康档案、风险评估和游客权限闭环上，新增可实际使用的个性减脂计划。系统根据用户健康档案生成安全、可解释、可复现的四周计划预览；用户确认后计划才生效，并成为后续“今日”执行中心、饮食记录和健康报告的目标来源。

本阶段只完整实现 `FAT_LOSS` 减脂目标。增肌、维持体重和改善饮食继续保留在健康档案中，但暂不生成对应计划。核心数值由 Spring Boot 规则引擎计算，Flutter 不自行决定健康目标，AI 不参与核心数值计算。

## 2. 已确认产品决策

- 减脂计划的主要入口为底部导航“计划”。
- 健康档案完成且未命中风险拦截后，直接进入减脂方案预览。
- 页面采用“A：摘要优先”结构，先展示关键目标，再按需查看计算依据和调整项。
- 用户必须点击“确认采用计划”，预览不会自动生效。
- 计划采用“长期目标 + 四周执行阶段”。
- 系统计算为主，用户只可在安全范围内有限调整。
- 后端保存权威结果和历史版本；App 只负责采集、展示和操作。
- 健康档案关键数据变化后只标记需要重算，不静默覆盖当前计划。

## 3. 用户流程

### 3.1 首次生成

1. 用户完成七步健康档案。
2. 若命中健康风险，停止普通减脂流程并显示风险说明。
3. 若目标不是减脂，“计划”页显示对应计划尚未开放，不伪造结果。
4. 若目标为减脂，App 请求计划预览。
5. 后端读取档案和最新体重，执行完整性、风险和安全校验。
6. 后端返回计划摘要、计算依据、安全说明和建议目标日期。
7. 用户可查看依据、在允许范围内调整，或点击“确认采用计划”。
8. 后端重新基于当前档案计算并保存正式计划；App 进入“今日”页。

预览与确认之间若档案发生变化，以确认时重新计算的服务端结果为准。服务端不得接受客户端直接提交 BMI、BMR、TDEE 或营养结果。

### 3.2 执行与调整

- 当前计划展示四周阶段、每日目标、本周重点和完成进度入口。
- 用户可调整目标热量、饮水、运动和睡眠；所有调整都由后端重新校验。
- 调整成功创建新版本，旧版本只读保留。
- 用户修改体重、身高、活动水平、目标体重、目标日期或代谢计算依据后，当前计划标记为“需要重新计算”。
- 用户确认重算后创建新版本；拒绝重算时旧计划继续展示，但明确标记可能不再匹配当前档案。
- 暂停后不再向“今日”页提供执行目标；恢复后继续当前四周阶段，不补造暂停期间的数据。

## 4. 页面结构与状态

“计划”页采用已确认的摘要优先布局，内容区圆角统一为 6px：

1. 标题、计划状态和当前第几周。
2. 深绿色关键摘要卡：每日目标热量、预计减重速度、四周阶段。
3. 四个目标卡：蛋白质、饮水、运动、睡眠。
4. “为什么这样安排”：展开 BMI、基础代谢、每日消耗、热量缺口、公式版本和安全说明。
5. 营养分配：蛋白质、碳水、脂肪的比例与克数。
6. 主操作：生成、确认采用、重新计算、恢复计划等当前唯一主要动作。
7. 次要操作：调整目标、暂停计划和查看历史版本。

页面必须覆盖以下状态：

| 状态 | 展示与操作 |
| --- | --- |
| 无计划 | 说明价值并提供“生成减脂计划” |
| 预览 | 展示完整摘要、依据、调整和“确认采用计划” |
| 执行中 | 展示当前版本、四周阶段、目标、调整、重算和暂停 |
| 需要重算 | 保留旧计划，突出显示档案变化和“重新计算” |
| 已暂停 | 显示暂停时间和“恢复计划” |
| 风险拦截 | 不展示普通减脂数值，说明原因并提供“返回修改档案” |
| 网络失败 | 保留已缓存计划，显示“暂时无法更新”和重试 |

游客点击生成或操作计划时沿用统一权限入口：先登录，再完成健康档案，最后回到计划预览。游客可浏览明确标记为“示例”的页面，但不得看到伪装成个人计算的数值。

## 5. 计算规则 v1

规则标识固定为 `FAT_LOSS_V1`。相同输入、调整项和规则版本必须产生相同结果。所有中间计算使用高精度十进制，API 展示值在最后一步统一舍入。

### 5.1 输入

- 出生日期与计算日期，用于得到周岁。
- 身高（厘米）。
- 最新体重测量（千克）。
- 生理代谢计算依据：`MALE` 或 `FEMALE`。
- 活动水平：`LOW`、`LIGHT`、`MODERATE`、`HIGH`。
- 当前睡眠时长和每周运动天数。
- 减脂目标体重和目标日期。
- 风险评估结果和健康档案版本。

当档案性别为男或女时，代谢计算依据自动使用对应值且不额外询问。当性别为“其他”时，健康档案增加必选的“代谢计算依据：男性公式 / 女性公式”；该值只用于能量估算，不改变用户展示的性别。

### 5.2 BMI 与基础代谢

```text
BMI = 体重kg / (身高m × 身高m)

男性公式 BMR = 10 × 体重kg + 6.25 × 身高cm - 5 × 年龄 + 5
女性公式 BMR = 10 × 体重kg + 6.25 × 身高cm - 5 × 年龄 - 161
```

基础代谢采用 Mifflin–St Jeor 公式。它是估算值，不表达为医学检测结果。参考：[Mifflin 等人的原始研究](https://pubmed.ncbi.nlm.nih.gov/2305711/)和 [NCBI Endotext 公式表](https://www.ncbi.nlm.nih.gov/books/NBK278991/table/diet-treatment-obes.table12est/)。

### 5.3 每日消耗与目标热量

第一版活动系数作为版本化产品规则保存：

| 活动水平 | 系数 |
| --- | ---: |
| 很少活动 `LOW` | 1.20 |
| 轻度活动 `LIGHT` | 1.375 |
| 中等活动 `MODERATE` | 1.55 |
| 高强度活动 `HIGH` | 1.725 |

```text
TDEE = BMR × 活动系数
基础目标热量 = TDEE × 0.80
目标热量 = max(基础目标热量, TDEE - 750, BMR, 性别安全下限)
```

安全下限采用更保守的产品阈值：男性公式 1500 kcal/日，女性公式 1200 kcal/日。系统不允许调整到 BMR 或对应安全下限以下，也不允许每日缺口超过 750 kcal。规则比国家卫健委指南给出的部分限能量方案更保守；产品不提供极低能量饮食方案。参考：[《成人肥胖食养指南（2024年版）》](https://wjw.baoji.gov.cn/col2223/col2269/202403/P020241228641521653546.pdf)。

预计速度按能量差估算，仅作为计划说明：

```text
预计每周变化kg = (TDEE - 目标热量) × 7 / 7700
```

目标日期早于安全估算日期时，后端返回建议日期和中文说明，不能用扩大热量缺口来追赶日期。国家卫健委公开材料建议合理减重速度约为每月 2–4kg；本产品还要同时满足当前体重每周变化不超过 1% 的更保守约束。

展示舍入统一为：BMI 保留 1 位小数，预计每周变化保留 2 位小数，BMR、TDEE、热量及三大营养素取整数，饮水取最接近的 100 ml。生成的目标热量取最接近的 10 kcal；安全校验始终使用舍入前数值。

### 5.4 营养、饮水、运动与睡眠

第一版均衡减脂计划默认供能比例：蛋白质 25%、碳水 50%、脂肪 25%。换算方式：

```text
蛋白质g = 目标热量 × 25% / 4
碳水g   = 目标热量 × 50% / 4
脂肪g   = 目标热量 × 25% / 9
```

- 饮水目标：体重 × 30 ml，限制在 1500–3500 ml/日；用户可按 100 ml 调整，但不能越界。特殊疾病用水需求不由本产品自动处理。
- 运动目标：默认每周至少 3 天、累计 150 分钟中等强度；结合当前运动天数逐步安排，不直接生成高强度训练处方。
- 睡眠目标：默认 7–9 小时，基于当前睡眠取最近的安全目标，按 0.5 小时调整。
- 第一版低碳水、高蛋白和素食偏好只用于后续饮食推荐，不改变上述核心默认比例，避免在尚无完整食物系统时生成不一致承诺。

### 5.5 阻断条件

以下任一情况不生成普通减脂计划：

- 健康档案未完成或缺少必要输入。
- 年龄不足 18 岁。
- 孕期、哺乳期、进食障碍风险或严重慢性病。
- 风险问卷已标记不安全目标。
- 当前 BMI 低于 18.5。
- 目标体重不低于当前体重、对应 BMI 低于 18.5 或目标日期无效。
- 性别为“其他”但未选择代谢计算依据。

阻断响应使用稳定错误码和中文说明，不返回可被误认为有效计划的部分数值。

## 6. 有限调整规则

- 热量目标允许按 50 kcal 为步长调整，仍需满足 BMR、安全下限和最大缺口。
- 蛋白质、碳水和脂肪不分别手填，随目标热量自动换算。
- 饮水按 100 ml 调整，范围为 1500–3500 ml。
- 每周运动天数为 0–7 的选择项，周时长按 30 分钟为步长；系统对突然大幅增加给出提醒。
- 睡眠目标按 0.5 小时调整，范围为 7–9 小时。
- 每次有效调整创建新版本，并记录调整前后值和原因；非法调整不写库。

## 7. 后端结构

### 7.1 组件

- `PlanCalculator`：纯计算组件，无数据库和网络依赖，输入快照并返回计算结果。
- `PlanPolicy`：完整性、风险、安全范围和状态转换校验。
- `PlanService`：读取用户档案、生成预览、确认、版本化、重算、暂停和恢复。
- `PlanController`：认证后的 HTTP 接口，只从认证主体取得用户 ID。

计算和策略可放在同一 `plan` 模块内，不创建单实现接口、插件系统或动态规则后台。

### 7.2 数据模型

新增健康档案字段：

```text
health_profiles.metabolic_basis VARCHAR(16) NULL
```

新增两张表：

```text
health_plans
- id, user_id（唯一，一个用户只有一份当前计划）
- status: ACTIVE / PAUSED
- phase_start_date, phase_end_date
- current_version
- paused_at, created_at, updated_at

health_plan_versions
- id, plan_id, version_number, rule_version
- profile_version, calculation_date
- 输入快照：age, metabolic_basis, height_cm, weight_kg, activity_level,
  target_weight_kg, requested_target_date
- 计算结果：bmi, bmr_kcal, tdee_kcal, target_kcal,
  protein_g, carbs_g, fat_g, water_ml,
  exercise_days, exercise_minutes, sleep_hours,
  expected_weekly_change_kg, suggested_target_date
- adjustment_reason, created_at
```

同一用户只允许一份当前计划。调整和重算只增加版本，不覆盖历史行。第一版不新增 `daily_targets`、`plan_rules` 或 `plan_adjustments` 表：固定规则版本存在代码中，版本行已经能够保存结果和调整原因；“今日”阶段真正需要按日变化时再增加每日目标表。

### 7.3 API

```text
POST /api/v1/plans/preview
POST /api/v1/plans
GET  /api/v1/plans/current
GET  /api/v1/plans/history
POST /api/v1/plans/{id}/recalculate
PUT  /api/v1/plans/{id}/targets
POST /api/v1/plans/{id}/pause
POST /api/v1/plans/{id}/resume
```

- `preview` 只计算不写入计划表。
- `POST /plans` 接收可选的有限调整值，重新读取当前档案并计算后保存，不能信任客户端预览数值。
- `current` 无计划时返回明确空状态，不使用异常表达正常状态。
- `history` 第一版返回版本摘要列表，不做复杂分页界面；接口保留简单页数限制防止无界返回。
- 所有按 ID 操作同时限定认证用户，其他用户的计划统一不可见。
- 写操作使用事务；暂停、恢复、调整和重算校验当前状态，重复请求得到稳定结果或明确冲突响应。

## 8. Flutter 集成

- 扩展现有 `ApiClient`，增加计划预览、确认、查询、调整、重算、暂停和恢复方法。
- `PlanPage` 从占位页替换为状态化页面，使用现有主题、6px 圆角、中文文本和统一权限入口。
- 不增加新的状态管理依赖；沿用当前 Riverpod 和会话控制方式。
- 健康档案选择“其他”时显示“代谢计算依据”二选一，并随档案保存。
- 健康档案完成且安全时，完成按钮改为“查看减脂方案”并打开“计划”页自动生成预览。
- 风险拦截时仍返回首页，不请求预览。
- 计划确认后进入“今日”页；“今日”阶段尚未实现前，只展示可验证的当前计划摘要入口，不伪造完成度。
- 当前计划成功加载后可做内存缓存；第一版不新增离线数据库。断网时只保留本次运行中已加载的数据，不能把过期示例当成当前计划。

## 9. 错误与安全处理

- 缺档案、风险阻断、不支持的目标、安全范围和状态冲突使用独立稳定错误码。
- 所有面向用户的文案为中文，不暴露 SQL、堆栈或内部类名。
- 计划接口只返回当前认证用户的数据；日志不记录完整健康档案。
- 计算结果明确标注“估算”和规则版本，不表达为诊断、治疗或处方。
- 网络失败不清空已展示计划；保存失败不在客户端假装成功。
- 并发调整按计划当前版本校验，旧版本请求返回冲突并要求刷新，避免静默覆盖。

## 11. 验收标准

- 完整且安全的减脂档案能够生成稳定计划预览，预览不写入正式计划。
- 用户确认后产生唯一当前计划和版本 1，并能重新查询。
- 计划页符合 A“摘要优先”布局和现有高级克制视觉风格，内容圆角为 6px。
- 热量和调整值不能突破安全边界，危险输入得到中文解释。
- 计划可调整、重算、暂停、恢复，并保留历史版本。
- 修改关键档案后旧计划不会被自动覆盖，而是显示需要重算。
- “其他”性别不改变显示身份，只有选择代谢计算依据后才能生成计划。
- 用户不能访问或修改其他账号的计划。
- 后端、Flutter 自动测试、静态检查和 Debug APK 构建全部通过。

## 12. 非目标

- 不在本阶段实现增肌、维持体重和改善饮食计划。
- 不生成逐餐食谱、采购清单或高强度训练处方。
- 不实现“今日”聚合、真实完成度、提醒、饮食记录或报告统计。
- 不让 AI 生成或修改核心健康数值。
- 不增加动态规则后台、离线数据库或复杂缓存层。
- 不处理疾病专用营养、药物、孕哺期、未成年人或进食障碍治疗方案。
