# 饮食记录与营养实时计算设计

日期：2026-09-08

## 1. 背景与目标

“轻食记”已经具备游客浏览、手机号登录、七步健康档案、减脂计划和今日执行中心，但 Flutter App 的“饮食”页仍是示例入口，后端也没有餐食持久化能力。

本阶段交付一个账号级、可跨设备同步的饮食记录闭环。用户可以按日期和餐次新增、编辑、删除食物，系统实时汇总热量、蛋白质、碳水和脂肪，并与用户已确认的减脂计划目标联动。后端保存权威数据，Flutter 负责高效录入、即时预览和中文状态展示。

## 2. 本轮范围

### 2.1 必须完成

- 约 40 种常见食物，覆盖主食、肉蛋奶、豆制品、蔬菜、水果和常见零食。
- 每种食物保存每 100 克营养数据，并可配置“1 个、1 碗、1 份”等常用份量。
- 早餐、午餐、晚餐、加餐四类记录。
- 内置食物搜索、最近吃过、常用食物。
- 新增、编辑、删除餐食。
- 自定义食物，并可保存为“我的食物”。
- 热量、蛋白质、碳水和脂肪实时计算。
- 与当前已确认减脂计划的营养目标联动。
- 日期切换与历史记录查看。
- 今日执行中心展示真实饮食进度，不再返回 `COMING_SOON`。
- 游客、未建档、无计划、空数据、网络失败和部分失败状态。
- 全中文、6px 圆角、窄屏、大字体和减少动态效果适配。

### 2.2 本轮不包含

- 饮水记录。
- 拍照 AI 识别。
- 条形码扫描。
- 第三方食物数据库。
- 七日或长期饮食趋势报告。
- 医疗诊断或医生级营养建议。

饮水继续作为独立功能，避免两个页面修改同一份数据。AI、条形码和第三方数据源在基础记录闭环稳定后单独设计。

## 3. 用户与权限

沿用现有三种状态：

`游客 → 已登录未建档 → 已登录已建档`

- 游客可以查看饮食页结构和示例说明，不能读取或写入个人记录。
- 游客点击记录操作时先进入登录，再进入健康档案，完成后返回饮食功能。
- 已登录但未完成健康档案的用户先补全档案。
- 已完成档案的用户可以记录饮食，即使尚未生成减脂计划。
- 没有减脂计划时只显示真实摄入总量和“生成减脂计划”入口，不展示默认目标或虚假完成比例。
- 所有用户级查询和变更必须以服务端认证身份为准，不接受客户端传入任意用户 ID。

## 4. 产品流程

### 4.1 浏览当天记录

用户进入“饮食”页后默认读取本地日期对应的数据。页面一次返回四餐记录、全天汇总、当前计划目标和页面状态。用户可切换前后日期或返回今天。

未来日期允许查看空状态，但不允许新增、编辑或删除记录。

### 4.2 添加内置食物

1. 用户点击页面固定操作区或某餐次内的“添加”。
2. 底部弹层默认按本地时间推荐餐次，用户可以切换。
3. 首屏显示最近吃过和常用食物，也可搜索内置食物。
4. 用户选择常用份量，或直接输入克数。
5. Flutter 根据食物每 100 克数据即时预览本次营养。
6. 用户确认后提交后端。
7. 后端重新计算并保存营养快照，返回更新后的全天数据。

默认餐次建议仅用于减少操作，不替用户做不可撤销决定。建议时段为：05:00–10:29 早餐、10:30–14:29 午餐、14:30–17:29 加餐、17:30–23:59 晚餐、00:00–04:59 加餐。

### 4.3 编辑与删除

编辑复用添加弹层，保存时更新原记录，不生成重复条目。删除前显示中文确认，删除成功后立即刷新本餐小计和全天汇总。

删除采用 `deleted_at` 标记。默认查询不返回已删除记录，为后续误删恢复和审计保留数据基础；本阶段不提供用户侧恢复入口。

### 4.4 自定义食物

搜索无结果时可进入“自定义食物”。用户填写名称、基准克数以及热量、蛋白质、碳水和脂肪，并选择是否保存为“我的食物”。未保存的自定义食物仍可作为本次餐食快照提交，但不会出现在后续搜索结果中。

## 5. Flutter 页面设计

### 5.1 页面结构

饮食页保持当前品牌的深绿色、大留白和克制信息层级，圆角统一为 6px。

1. 顶部：标题、当前日期、前一天、后一天和返回今天。
2. 今日摄入总览：一张主卡显示热量，横向显示蛋白质、碳水和脂肪。
3. 计划状态：有计划时显示真实目标与进度；无计划时显示入口；风险拦截时不展示普通减脂目标。
4. 餐次列表：早餐、午餐、晚餐、加餐可折叠，每组显示小计、条目和添加按钮。
5. 底部操作：在底部导航上方提供“添加食物”，避免遮挡系统安全区和导航。

### 5.2 高效录入

- 搜索前优先展示最近吃过和常用食物。
- 常用份量以可点击标签呈现，例如“半碗”“1 碗”“1 个”“150 克”。
- 选中份量后自动换算克数；用户需要精确记录时才打开数字键盘。
- 营养预览随份量或克数变化，不需要先提交。
- 保存期间禁用重复点击，并显示局部加载状态。

### 5.3 状态与情绪表达

- 无记录：提示“记录第一餐，看看今天的营养进度”。
- 无计划：展示摄入量，不显示百分比，提供“生成减脂计划”。
- 超出目标：保留真实数值，使用温和说明，不用大面积红色制造焦虑。
- 网络失败：保留最近成功加载的内容并标记“数据可能不是最新”，提供“重新加载”。
- 保存失败：保留用户填写内容，不关闭弹层，不伪装成功。
- 减少动态效果开启时取消非必要进度动画和弹层过渡增强。

## 6. 后端数据模型

新增 Flyway V5 迁移，包含三张核心表。

### 6.1 `foods`

- `id`
- `owner_user_id`：空值表示系统内置食物，非空表示用户自定义食物。
- `name`
- `category`
- `calories_per_100g`
- `protein_per_100g`
- `carbs_per_100g`
- `fat_per_100g`
- `created_at`、`updated_at`、`deleted_at`

系统食物不可由普通用户修改。用户自定义食物只对创建者可见。

### 6.2 `food_portions`

- `id`
- `food_id`
- `label`：例如“1 碗”。
- `grams`
- `sort_order`

常用份量最终统一换算为克数参与计算。

### 6.3 `meal_entries`

- `id`
- `user_id`
- `entry_date`
- `meal_type`：`BREAKFAST`、`LUNCH`、`DINNER`、`SNACK`。
- `food_id`：临时自定义食物允许为空。
- `food_name_snapshot`
- `grams`
- `calories_snapshot`
- `protein_snapshot`
- `carbs_snapshot`
- `fat_snapshot`
- `idempotency_key`
- `created_at`、`updated_at`、`deleted_at`

餐食保存营养快照。以后修正食物库数据时，历史记录不会被静默改写。

## 7. 营养计算

内置食物统一保存每 100 克数据：

`本次营养 = 每 100 克营养 × 本次克数 ÷ 100`

- 服务端使用十进制定点数计算，不使用二进制浮点数作为持久化依据。
- 单条与汇总的热量显示为整数，三大营养素显示一位小数。
- 汇总先使用未展示舍入值累加，再在响应层统一舍入，避免多条记录累计误差。
- Flutter 的即时预览使用同一公式；保存后以后端响应替换预览值。
- 计划目标只读取当前 `ACTIVE` 计划版本，不回退到统一默认值。

## 8. API 设计

所有接口位于 `/api/v1`，沿用 Bearer Token 和现有中文错误结构。

### 8.1 食物

- `GET /foods?query=&scope=&limit=`：搜索系统食物和当前用户的自定义食物。
- `GET /foods/suggestions?limit=`：分别返回当前用户最近吃过和按记录频率计算的常用食物。
- `POST /foods/custom`：创建“我的食物”。

搜索结果包含食物基础营养和常用份量。`scope` 支持 `ALL`、`SYSTEM`、`MINE`。

### 8.2 每日饮食

- `GET /nutrition/days/{date}`：返回四餐、全天汇总、计划目标和状态。
- `POST /nutrition/entries`：新增餐食。
- `PUT /nutrition/entries/{id}`：编辑餐食。
- `DELETE /nutrition/entries/{id}`：删除餐食。

新增和编辑成功后直接返回更新后的每日饮食响应，客户端无需再发一次读取请求。

写接口接收 `Idempotency-Key` 请求头。相同用户、相同键的重复新增请求返回第一次成功结果，不创建重复记录。
数据库对 `user_id + idempotency_key` 建立唯一约束，服务端同时处理并发重复请求。

### 8.3 今日执行中心

`GET /today?date=YYYY-MM-DD` 的 `nutrition` 模块改为返回：

- `status`：`READY`、`EMPTY`、`ERROR`。
- `consumedKcal`
- `targetKcal`：没有有效计划时为空。
- `proteinG`、`carbsG`、`fatG`
- `message`：仅错误或需要解释的状态返回中文内容。

饮食模块失败不得阻止计划、体重等其他今日模块返回。

## 9. 校验、安全与错误处理

- 写入餐食前必须登录并完成健康档案。
- 所有条目更新和删除都同时按 `id` 与当前 `user_id` 查询。
- 内置食物 ID 必须存在且未删除；用户食物必须属于当前用户。
- 食物名称必填，最多 30 个字符。
- 克数必须大于 0，最多 5000 克。
- 热量和三大营养素必须为非负值，并设置合理数据库上限。
- 未来日期禁止新增、编辑和删除。
- 服务端不相信客户端提交的内置食物营养值，必须按食物库重新计算。
- 自定义食物的营养值在信任边界重新校验。
- 保存失败返回稳定错误码和中文提示，不暴露堆栈、SQL 或内部表名。
- 列表按餐次和创建时间稳定排序。

## 10. 缓存与一致性

Flutter 可按“用户＋日期”保存最近成功响应的内存缓存，用于页面切换和短暂网络失败。缓存不得跨账号复用，退出登录或页面提供器销毁时释放。

写操作使用后端返回的完整当日结果替换对应缓存。并发切换日期时，只允许当前选中日期的最新请求更新可见页面，较旧响应必须丢弃。

## 11. 测试与验收

### 11.1 后端

- V5 在空库以及 V4 升级场景中迁移成功。
- 食物搜索范围、最近食物去重和用户自定义食物隔离正确。
- 常用份量换算和服务端营养计算准确。
- 新增、编辑、删除后返回的餐次小计和全天汇总正确。
- 营养快照不随食物库后续修改而改变。
- 无计划时不返回伪造目标。
- 未登录、未建档、跨用户访问、未来日期和非法数值被拒绝。
- 重复 `Idempotency-Key` 不产生重复餐食。
- 今日接口返回真实营养状态，且饮食失败不影响其他模块。

### 11.2 Flutter

- 游客受限流程能返回饮食功能。
- 日期切换、四餐折叠、搜索、最近食物和常用份量可操作。
- 份量与克数变化时即时预览正确。
- 新增、编辑、删除后界面和汇总同步更新。
- 保存失败保留输入内容，读取失败可重试并正确标记旧数据。
- 无计划、风险拦截、空记录和未来日期状态正确。
- 账户与日期缓存隔离，在途旧响应不会覆盖新页面。
- 中文语义标签、窄屏、大字体和减少动态效果通过测试。
