# 轻食记 Web 管理端设计规格

日期：2026-10-26

## 1. 背景与目标

轻食记已经具备 Flutter 用户端、Spring Boot 后端和完整的健康记录主流程，但尚无管理端。作为毕业设计，系统需要补齐管理员角色、运营概览、用户治理、食物库维护、注销监管和操作追溯，同时避免扩展成通用运营平台。

本阶段新增一个由 Spring Boot 直接托管的原生 Web 管理端。管理员可以查看运营数据，管理用户状态和系统食物，在填写原因后查看用户完整健康档案与指定日期范围内的饮食明细，审核用户自定义食物是否进入系统食物库，并只读查看注销申请。所有敏感读取和管理写操作必须可追溯。

实现遵循 ponytail 原则：复用现有 `JdbcTemplate`、BCrypt、令牌哈希、统一错误结构和数据库，不新增前端框架、图表库、ORM、消息队列或权限平台。

## 2. 已确认方案

- 管理端采用独立管理员账号，不把普通用户提升为管理员。
- 第一个管理员由环境变量在首次启动时初始化。
- 管理员可以查看用户完整健康档案和饮食明细；每次查看前必须填写访问原因。
- 食物管理覆盖系统食物维护和用户自定义食物入库审核。
- 自定义食物创建后仍由用户立即私有使用；审核通过后复制为系统食物，驳回不影响私有使用。
- 注销申请只读监管，不允许管理员批准、驳回、取消或提前执行。
- 看板提供核心数字及最近 7 天用户注册、饮食记录趋势。
- 页面采用左侧导航、清新品牌绿、中文界面和 6 px 主控件圆角。
- 管理端由 Spring Boot 内置静态资源提供，访问入口为 `/admin/`。

## 3. 本期范围

### 3.1 包含

- 独立管理员初始化、登录、退出和 8 小时访问令牌。
- 数据看板：用户总数、今日活跃用户、今日饮食记录、待审核食物、注销处理中数量。
- 最近 7 天新增用户与饮食记录趋势。
- 用户搜索、分页、状态筛选、禁用和恢复。
- 管理员填写原因后查看用户完整档案、最新身体测量、目标、饮食偏好、风险信息和最多 31 天饮食明细。
- 系统食物搜索、新增、编辑、停用、恢复和份量维护。
- 用户自定义食物待审核列表、通过发布和驳回。
- 注销申请分页、筛选和详情只读查看。
- 管理员操作日志分页和筛选。
- 原生 HTML、CSS、JavaScript 管理页面及中文错误、加载和空状态。

### 3.2 不包含

- 多管理员角色、动态权限、RBAC 配置页或管理员自助注册。
- 刷新令牌、记住登录、单点登录、验证码或找回管理员密码。
- 用户数据导出、管理员直接删除用户、提前执行或取消注销。
- 批量禁用、批量审核、批量导入食物或 Excel 导出。
- 管理员修改用户健康数据、饮食记录、计划或报告。
- 运动、睡眠、饮水、计划和报告趋势图。
- Vue、React、Node 构建链、前端路由库或图表库。
- 会员、支付、AI、家庭成员或客服工单。

## 4. 总体架构

管理端与现有应用共用一个 Spring Boot 进程和数据库：

```text
浏览器 /admin/
      │ 原生 HTML/CSS/JS
      │ Bearer 管理员令牌
      ▼
/api/v1/admin/**
      │
Spring Boot + JdbcTemplate
      │
MySQL / H2 测试数据库
```

页面文件固定为：

- `static/admin/index.html`
- `static/admin/admin.css`
- `static/admin/admin.js`

页面使用一个壳层和五个内容面板，通过原生 JavaScript 切换，不引入客户端路由。登录状态保存在 `sessionStorage`，关闭浏览器后自然清除。Spring MVC 仅为 `/admin/` 提供静态首页转发；静态资源本身不要求登录，数据 API 必须认证。

后端按职责保持少量类：管理员认证、看板、用户管理、食物管理、注销查询和审计查询。各服务直接使用现有 `JdbcTemplate` 与业务表，不建立第二套领域模型。

## 5. 管理员认证与权限边界

### 5.1 初始化

应用启动时读取：

- `ADMIN_USERNAME`
- `ADMIN_PASSWORD`

仅当 `admin_users` 为空且两个变量均非空时，创建第一个管理员并使用现有 `PasswordEncoder` 写入 BCrypt 哈希。已有管理员时不得覆盖密码或重复创建。变量缺失时应用仍可启动，但记录不含密码的中文警告，管理端无法登录。

初始化用户名去除首尾空格后长度为 3–64 个字符，密码至少 12 个字符。不满足要求时不得创建管理员，也不得把原始值写入日志。

仓库只在 `.env.example` 和 README 中记录变量名，不提交真实账号或密码。

### 5.2 登录令牌

- 登录成功后签发随机管理员访问令牌，数据库仅保存 SHA-256 哈希。
- 令牌有效期固定为 8 小时。
- 不签发刷新令牌；到期后重新登录。
- 退出登录撤销当前令牌。
- 浏览器只在 `sessionStorage` 保存明文令牌，不写 Cookie 或 `localStorage`。

### 5.3 Spring Security

- `/admin/**` 和 `/api/v1/admin/auth/login` 允许未认证访问。
- 其余 `/api/v1/admin/**` 必须具有 `ROLE_ADMIN`。
- 管理员令牌由独立过滤器验证并建立管理员身份。
- 普通用户令牌没有管理员权限，访问管理 API 返回 `403`。
- 管理员令牌不得访问普通用户私有 API。

管理员 API 继续使用现有统一 `{code, message}` 错误结构，不返回 SQL、异常堆栈、密码哈希或令牌哈希。

## 6. 数据模型与 V14 迁移

全部数据库变化集中在 `V14__create_admin_web.sql`，不得占用后续迁移号。

### 6.1 `admin_users`

保存：管理员 ID、唯一用户名、显示名、密码哈希、`ACTIVE` 或 `DISABLED` 状态、最后登录时间、创建和更新时间。

用户名规范化后唯一。第一版不提供页面内新增、删除、改密或禁用管理员的能力。

### 6.2 `admin_access_tokens`

保存：令牌 ID、管理员 ID、唯一令牌哈希、到期时间、撤销时间和创建时间。外键关联管理员，按令牌哈希建立唯一索引。

### 6.3 `admin_audit_logs`

追加保存：日志 ID、管理员 ID、操作类型、目标类型、可空目标 ID、可空访问原因、简短详情和创建时间。

目标 ID 不建立到业务表的外键，避免用户按既有注销流程永久删除后阻断清理或级联删除审计事实；日志本身不得保存手机号或健康数据正文。

审计日志只记录成功的管理写操作、敏感读取、登录和退出。第一版不为失败操作引入独立事务或第二套安全事件系统。管理 API 不提供修改或删除日志的接口。

### 6.4 `foods` 增量

只为用户自定义食物增加入库审核信息：审核状态、审核管理员、审核时间、审核意见和可空的已发布系统食物 ID。

- 系统食物的审核字段为空。
- 现有和新增自定义食物初始化为 `PENDING`。
- 通过后为 `APPROVED` 并关联新建的系统食物。
- 驳回后为 `REJECTED`，原自定义食物仍对创建者可用。
- 同一自定义食物只能从 `PENDING` 审核一次。

### 6.5 用户状态

复用现有 `users.status`，新增业务值 `DISABLED`，不新增角色列：

- 禁用只允许 `ACTIVE → DISABLED`。
- 恢复只允许 `DISABLED → ACTIVE`。
- 管理员不得修改 `DELETION_PENDING`。
- 禁用成功时撤销该用户全部设备、访问令牌和刷新令牌。
- 恢复后旧令牌不恢复，用户必须重新登录。

## 7. 页面与交互

### 7.1 登录

登录页包含用户名、密码和登录按钮。请求期间按钮禁用；失败时显示服务端中文错误。登录成功进入看板，`401` 或令牌过期时清除 `sessionStorage` 并返回登录页。

### 7.2 布局

桌面端采用固定左侧导航：

1. 数据看板。
2. 用户管理。
3. 食物管理。
4. 注销申请。
5. 操作日志。

顶部显示当前模块、管理员显示名和退出入口。视觉沿用品牌绿、白色内容区、低饱和状态色和 6 px 圆角。窄屏允许导航收起，但第一版以桌面浏览器答辩演示为主。

### 7.3 数据看板

核心卡片：

- 用户总数。
- 今日活跃用户：当天 `user_devices.last_seen_at` 有更新的去重用户。
- 今日有效饮食记录数。
- `PENDING` 自定义食物数。
- `PENDING` 注销申请数。

最近 7 天趋势只展示每日新增用户和每日有效饮食记录。现有数据没有每日活跃历史快照，因此不绘制虚假的历史活跃趋势，也不新增统计表。

趋势图使用 CSS 与原生 SVG 或简单表格呈现，不引入图表依赖。

### 7.4 用户管理

普通列表展示脱敏手机号、昵称、账户状态、注册时间、档案是否完成、饮食记录数量和最近活跃时间。支持关键词、状态、页码和每页数量查询，每页最多 50 条。

禁用和恢复必须二次确认。服务端使用带原状态条件的更新；状态已变化时返回 `409` 中文冲突错误。

敏感详情必须先弹出“访问原因”输入框。提交后一次返回：

- 完整手机号和账户摘要。
- 完整健康档案字段。
- 最新身体测量。
- 健康目标。
- 饮食偏好。
- 最新风险信息。
- 指定日期范围内的有效饮食明细。

饮食日期范围不能为空且最多 31 天。请求成功后服务端写入一条包含原因和查询区间的审计日志。管理端只能查看，不能修改这些数据。

访问原因去除首尾空格后必须为 5–200 个字符。离开详情、退出登录或收到 `401` 时，页面立即清除内存中的敏感详情。

### 7.5 食物管理

系统食物支持搜索、分类筛选、新增、编辑、停用和恢复。新增或编辑在同一表单中维护名称、分类、每 100 克营养和常用份量。

- 营养范围复用现有 `FoodService` 校验上限。
- 系统食物名称继续保持唯一。
- 食物与份量在一个事务中保存。
- 已产生历史饮食记录的食物只能软停用，历史快照不改变。

自定义食物审核列表展示创建者脱敏手机号、食物名称、分类、营养值和创建时间。管理员可以：

- 通过：复制为新的系统食物，建立默认“100 克”份量，并把来源标为 `APPROVED`。
- 驳回：填写简短意见，把来源标为 `REJECTED`。

通过时若系统库已有同名食物，返回 `409`，来源保持 `PENDING`。管理员可以改为维护现有系统食物后驳回该申请。审核不会停用或修改用户的私有食物。

### 7.6 注销申请

只读展示申请用户、状态、申请时间、计划执行时间、恢复时间和完成时间。支持状态、日期和关键词筛选。

页面不提供批准、驳回、取消或提前执行按钮。现有“7 天冷静期、用户恢复、到期自动清理”语义保持不变。

### 7.7 操作日志

展示管理员、操作类型、目标、访问原因、详情和时间，支持管理员用户名、操作类型、目标 ID 和日期筛选。每页最多 50 条，不提供编辑、删除或导出。

## 8. API 契约

统一前缀为 `/api/v1/admin`。

### 8.1 认证

```text
POST /auth/login
POST /auth/logout
```

登录返回管理员显示名、访问令牌和到期时间。退出返回 `204`。

### 8.2 看板

```text
GET /dashboard
```

一次返回核心卡片和最近 7 天两组趋势，不拆分多个请求。

### 8.3 用户

```text
GET   /users?q=&status=&page=&size=
PATCH /users/{id}/status
POST  /users/{id}/sensitive-view
```

状态请求只接受 `DISABLED` 或 `ACTIVE`。敏感查看请求包含必填原因、开始日期和结束日期；日期范围最多 31 天。

### 8.4 食物

```text
GET  /foods?scope=&q=&category=&reviewStatus=&page=&size=
POST /foods/system
PUT  /foods/system/{id}
POST /foods/system/{id}/disable
POST /foods/system/{id}/restore
POST /foods/custom/{id}/review
```

审核请求只接受 `APPROVE` 或 `REJECT`；驳回时意见必填。重复审核返回 `409`。

### 8.5 注销与审计

```text
GET /deletion-requests?status=&q=&from=&to=&page=&size=
GET /audit-logs?admin=&action=&targetId=&from=&to=&page=&size=
```

两个模块均只读。

## 9. 事务、审计与并发

- 用户禁用、令牌撤销和审计写入在同一事务中完成。
- 用户恢复和审计写入在同一事务中完成。
- 敏感数据读取完成后，在返回响应前写入审计；审计写入失败则整个请求失败且不返回数据。
- 系统食物及份量保存使用单个事务。
- 自定义食物发布、默认份量创建、来源状态更新和审计写入使用单个事务。
- 状态变更和审核使用条件更新保证并发安全，不新增通用版本框架。
- 重复提交以当前数据库状态返回 `409`，前端刷新对应列表。

审计详情只记录必要摘要，例如状态变化、查询日期范围和发布后的系统食物 ID；不得记录密码、完整令牌、完整健康档案或完整饮食负载。

## 10. 错误与恢复

- 所有用户可见错误使用中文，保留稳定机器错误码。
- `400`：参数、访问原因、日期范围或营养值不合法。
- `401`：管理员令牌缺失、失效或过期；页面清除会话并返回登录。
- `403`：普通用户令牌或禁用管理员访问管理 API。
- `404`：用户、食物或审核对象不存在。
- `409`：状态已改变、重复审核或系统食物重名。
- `500`：统一显示“操作失败，请稍后重试”，服务端日志不得包含密码和令牌。

表单请求失败时保留输入；列表失败时保留筛选条件并提供重试。写操作只有服务端确认成功后才更新页面状态。

前端展示 API 数据时使用 DOM `textContent` 或等价安全属性，不把用户名、食物名、访问原因或健康字段拼入 `innerHTML`。

## 11. 测试与验收

### 11.1 迁移与认证

- V1 至 V14 全新迁移成功，V13 数据升级到 V14 成功。
- 仅数据库无管理员且环境变量齐全时创建首个管理员。
- 密码只存 BCrypt 哈希，令牌只存 SHA-256 哈希。
- 登录、退出、8 小时到期、撤销令牌和禁用管理员正确。
- 普通用户 Token 访问管理 API 返回 `403`。

### 11.2 用户与隐私

- 用户搜索、状态筛选、分页和脱敏正确。
- 只有 `ACTIVE` 可禁用，只有 `DISABLED` 可恢复。
- 禁用撤销全部用户会话，恢复不恢复旧会话。
- `DELETION_PENDING` 无法被管理员改为其他状态。
- 敏感查看无原因、空日期或超过 31 天时拒绝。
- 敏感查看只返回目标用户数据并写入访问原因和区间审计。
- 审计写入失败时不返回敏感数据。

### 11.3 食物、注销与看板

- 系统食物和份量增改、停用及恢复正确，营养校验复用现有边界。
- 审核通过创建系统副本和 100 克份量，私有来源仍可用。
- 驳回不影响私有食物，重复审核和同名发布返回 `409`。
- 注销查询不改变现有 7 天流程，也不存在管理写接口。
- 看板所有数字和最近 7 天趋势来自真实测试数据。

### 11.4 Web 与全量门禁

- `/admin/`、CSS 和 JavaScript 静态资源可访问。
- 在真实浏览器完成登录、导航、筛选、敏感原因弹窗、写操作确认、`401` 返回登录和退出冒烟验收。
- 不新增 Node 或浏览器自动化测试依赖。
- 运行后端全量测试、现有 Flutter 全量测试、`scripts/check.ps1`、`git diff --check` 和敏感文件扫描。

## 12. 实施顺序

1. 先写失败测试，再实现 V14、管理员初始化、登录、退出、令牌过滤和审计基础。
2. 先写失败测试，再实现看板、用户、敏感查看、食物、注销和审计 API。
3. 实现一个 HTML、一个 CSS 和一个 JavaScript 文件，完成五个管理模块。
4. 执行定向测试、全量门禁和真实浏览器冒烟验收。

每一阶段只复用现有工具和依赖。发现必须新增框架、迁移超过 V14 或改变现有用户/注销语义时，停止实施并重新确认范围。

## 13. 完成标准

- 启动 Spring Boot 后可通过 `/admin/` 完成所有本期管理操作。
- 管理员和普通用户身份严格隔离。
- 所有管理写操作和敏感读取可追溯，敏感读取必须有原因。
- 用户禁用、恢复和注销监管不破坏现有账户生命周期。
- 食物审核只决定是否进入系统库，不妨碍用户私有使用。
- 看板不展示模拟数据或无法由现有数据准确计算的指标。
- 页面使用已确认的左侧导航、品牌绿、中文和 6 px 圆角。
- 实现不包含本期未确认的框架、角色、批量、导出、支付、会员或 AI 能力。
