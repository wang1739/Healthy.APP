# 轻食记 Healthy 可行性分析报告

文档编号：LB-PM-002
版本：1.0
日期：2026-09-07
结论：可行

## 1. 分析目的

本报告评估轻食记正式上线版在技术、经济、运营、进度、法律合规和风险方面的可行性。评估范围与《项目建议书》一致，基线版本为 v1.0.0。

## 2. 技术可行性

### 2.1 技术路线

| 层级 | 方案 | 可行性判断 |
|---|---|---|
| 移动端 | Flutter，Android/iOS 共用领域与界面代码 | 成熟，适合中小团队多端交付 |
| Web | 轻量品牌站、账户与报告页 | 范围受控，无需复制完整 App |
| 后端 | Java 17、Spring Boot、模块化单体 | 生态成熟，边界清楚，运维成本可控 |
| 数据 | MySQL、Redis、私有对象存储 | 满足事务、缓存、会话和图片文件需求 |
| 集成 | 短信、微信、Apple、支付、AI、推送适配器 | 可替换并可在测试环境使用替身 |
| 交付 | 容器、CI/CD、灰度、监控和自动备份 | 支持可重复部署与快速回滚 |

采用模块化单体而非微服务，减少分布式事务、部署和观测复杂度。按业务能力分包，可在确有容量或组织需求后独立拆分。

### 2.2 关键技术难点

- 健康目标安全性：通过纯计算规则、版本化参数、边界测试和风险拒绝策略解决。
- 离线与多设备同步：通过客户端队列、幂等操作号、服务端版本和显式冲突处理解决。
- 健康平台同步：通过来源 ID、同步游标、授权状态及手动录入兜底解决。
- AI 不确定性：识别结果只作为候选，必须经用户确认才形成记录。
- 支付一致性：通过订单状态机、回调验签、幂等处理、补偿和每日对账解决。

结论：不存在无法实现的核心技术障碍，技术风险可通过隔离、测试和降级控制。

## 3. 经济可行性

### 3.1 成本构成

| 成本项 | 主要内容 | 控制方式 |
|---|---|---|
| 研发 | 产品、客户端、后端、测试、安全、运维 | 分阶段交付，复用 Flutter 与开源生态 |
| 云资源 | 计算、数据库、Redis、存储、CDN、备份 | 小规格起步，按真实容量扩展 |
| 第三方 | 短信、AI 识别、推送、支付通道 | 配额、缓存、供应商比价和失败降级 |
| 合规发布 | 备案、隐私审查、应用市场和证书 | 前置准备，避免临发布返工 |
| 运维支持 | 监控、告警、客服、恢复演练 | 自动化和标准运行手册 |

首发可使用单体应用和托管数据服务，基础环境按月弹性支出。AI、短信和对象存储成本随活跃用户增长，会员权益和配额可限制单位用户成本。支付按交易计费，无需自建清算系统。

### 3.2 收益与价值

- 免费版降低获客门槛，Pro 和家庭版形成持续订阅收入。
- 可解释计划、完整健康闭环和家庭协作形成差异化价值。
- 统一代码与模块化架构降低重复开发、缺陷和运维成本。
- 数据导出、隐私控制和可靠服务有助于提升留存与信任。

结论：在分阶段投入、控制第三方额度并验证付费转化的前提下，经济上可行。

## 4. 运营可行性

产品流程符合普通用户从建档到每日执行的认知顺序，关键记录提供手动方式，不强制授予系统健康权限。管理后台覆盖食物库、内容、会员、订单、反馈和审计，客服能够在脱敏前提下处理问题。

运营前需要准备：正式客服渠道、内容审核规范、健康免责声明、退款流程、事件响应联系人和数据请求处理流程。通过灰度发布、指标看板和用户反馈闭环，可持续优化留存和计划完成率。

结论：具备可运营性，且日常运营不依赖研发直接修改数据库。

## 5. 进度可行性

项目按六个里程碑推进，每个里程碑均可独立演示和验证。建议完整交付投入约 30–42 人月，典型 6–8 人跨职能团队可在 6–8 个月完成；应用资质、备案和第三方审核与研发并行。范围变更必须经过 R-08 评审，不压缩安全、测试和恢复演练。

关键路径为：账户与档案 → 计划引擎 → 每日记录 → 报告 → 支付与发布。AI 食物识别和部分运营功能可在不影响核心闭环的情况下调整优先级。

结论：在资源稳定、外部资质按时到位的条件下，进度可行。

## 6. 法律与合规可行性

项目面向中国大陆，涉及手机号、身份标识、健康与交易信息，应落实：

- 明示目的、范围和保存期限，健康信息单独同意并支持撤回。
- 最小必要收集、首次同意前不初始化非必要 SDK。
- 个人信息查询、更正、导出、删除与账号注销渠道。
- 第三方 SDK、共享对象、处理目的和权限清单。
- 国内部署、域名与备案要求，跨境处理在发生前单独评估。
- 支付资质、回调验签、订单审计和退款处理。
- 健康免责声明和风险提示，避免宣传为诊疗工具。

结论：合规路径明确，但 R-04 属发布门禁；正式文本和实际处理活动必须在上线前完成专业审查。

## 7. 风险可行性

项目建议书列出的 R-01 至 R-08 均有预防、检测、响应和责任角色。高风险项设置发布门禁：健康规则未经测试、安全高危未关闭、隐私材料不完整、支付对账失败或恢复演练失败时不得上线。

## 8. 替代方案比较

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Flutter + 模块化单体 | 多端复用、交付快、运维简单 | 原生特性需插件与平台验证 | 推荐 |
| Android/iOS 双原生 + 微服务 | 平台控制力强、可独立扩容 | 人力、周期和运维成本高 | 当前不采用 |
| 纯 Web/PWA | 初期成本低、发布快 | 健康平台、通知和商店能力受限 | 仅适合作为补充 |

## 9. 总体结论

轻食记项目在技术、经济、运营、进度和合规方面总体可行。建议以 Flutter + Spring Boot 模块化单体为主路线，优先完成安全健康管理核心闭环，并将 R-01、R-02、R-03、R-04 设置为持续跟踪的高优先级风险和生产发布门禁。
